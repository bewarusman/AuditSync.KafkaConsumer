# Rules Engine Logging Guide

This document explains the step-by-step logging output generated by the rules engine when evaluating audit messages.

## Log Format Overview

The rules engine produces structured logs that show:
1. Which rules are being evaluated
2. Which conditions are checked for each rule
3. The actual vs expected values for each condition
4. Whether each condition passed or failed
5. Whether the overall rule matched
6. What actions were taken (createCase, extractions, etc.)

## Log Levels

- **Information**: Main flow (rule evaluation start/end, rule matched/not matched, condition results)
- **Debug**: Additional details (rules loaded from cache, audit log stored)
- **Warning**: Issues (empty operators, regex errors, invalid configuration)
- **Error**: Exceptions during evaluation

## Field Names Available for Conditions

The following field names can be used in rule conditions (case-insensitive):

| Field Name     | Maps to AuditMessage Property | Type   | Example Value                          |
|----------------|-------------------------------|--------|----------------------------------------|
| dbuser         | DbUser                        | string | DWH_USER                               |
| action         | Action                        | string | SELECT, INSERT, UPDATE, DELETE         |
| owner          | Owner                         | string | DWH_USER                               |
| name           | Name                          | string | SUBSCRIBERS                            |
| sqltext        | SqlText                       | string | SELECT * FROM SUBSCRIBERS WHERE...     |
| bindvariables  | BindVariables                 | string | :1 = '123456789', :2 = 'John'          |
| osuser         | OsUser                        | string | oracle                                 |
| userhost       | UserHost                      | string | app-server-01                          |
| terminal       | Terminal                      | string | pts/0                                  |
| returncode     | ReturnCode                    | int    | 0                                      |

## Operator Implementations

### String Operators

- **equals**: Case-sensitive exact match
  - Example: `Field='name', Operator='equals', Value='SUBSCRIBERS'`
  - Matches: `SUBSCRIBERS`
  - Does NOT match: `subscribers`, `SUBSCRIBER`

- **not_equals**: Case-sensitive, does not match
  - Example: `Field='name', Operator='not_equals', Value='SUBSCRIBERS'`
  - Matches: `PRODUCTS`, `subscribers`
  - Does NOT match: `SUBSCRIBERS`

- **contains**: Case-insensitive substring match
  - Example: `Field='sqlText', Operator='contains', Value='msisdn'`
  - Matches: `... WHERE MSISDN = ...`, `... msisdn ...`, `... MsIsdn ...`

- **not_contains**: Case-insensitive, does not contain substring
  - Example: `Field='sqlText', Operator='not_contains', Value='password'`
  - Matches: `SELECT * FROM USERS WHERE ID = :1`
  - Does NOT match: `... WHERE PASSWORD = ...`

- **starts_with**: Case-sensitive prefix match
  - Example: `Field='sqlText', Operator='starts_with', Value='SELECT'`
  - Matches: `SELECT * FROM ...`
  - Does NOT match: `select * FROM ...`, `INSERT INTO ...`

- **ends_with**: Case-sensitive suffix match
  - Example: `Field='name', Operator='ends_with', Value='_AUDIT'`
  - Matches: `USER_AUDIT`, `TRANSACTIONS_AUDIT`
  - Does NOT match: `USER_audit`, `AUDIT_LOG`

- **regex**: Regular expression match
  - Example: `Field='sqlText', Operator='regex', Value='WHERE\\s+MSISDN\\s*='`
  - Matches: `... WHERE MSISDN = ...`, `... WHERE  MSISDN=...`
  - Timeout: 1 second per regex evaluation

- **regex_in**: Matches any regex pattern from array
  - Example: `Field='sqlText', Operator='regex_in', Value=['WHERE\\s+MSISDN', 'WHERE\\s+EMAIL']`
  - Matches if ANY pattern matches
  - Returns false if all patterns fail

### Array Operators

- **in**: Value is in the list (case-insensitive)
  - Example: `Field='action', Operator='in', Value=['INSERT', 'UPDATE', 'DELETE']`
  - Also accepts CSV string: `Value='INSERT,UPDATE,DELETE'`
  - Matches: `INSERT`, `insert`, `UPDATE`
  - Does NOT match: `SELECT`

- **not_in**: Value is not in the list (case-insensitive)
  - Example: `Field='action', Operator='not_in', Value=['SELECT']`
  - Matches: `INSERT`, `UPDATE`, `DELETE`
  - Does NOT match: `SELECT`, `select`

### Null Operators

- **is_null**: Value is null or empty/whitespace
  - Example: `Field='bindVariables', Operator='is_null'`
  - Matches: `null`, `""`, `"   "`
  - Does NOT match: `"test"`, `"0"`

- **is_not_null**: Value is not null and not empty
  - Example: `Field='bindVariables', Operator='is_not_null'`
  - Matches: `"test"`, `"0"`, `"   a   "`
  - Does NOT match: `null`, `""`, `"   "`

### Numeric/DateTime Operators

- **gt** or **greater_than**: Greater than (numeric comparison)
  - Example: `Field='returnCode', Operator='gt', Value=0`
  - Matches: `1`, `100`, `999`
  - Does NOT match: `0`, `-1`

- **lt** or **less_than**: Less than (numeric comparison)
  - Example: `Field='returnCode', Operator='lt', Value=5`
  - Matches: `0`, `1`, `4`
  - Does NOT match: `5`, `10`

- **gte** or **greater_than_or_equal**: Greater than or equal (numeric comparison)
  - Example: `Field='returnCode', Operator='gte', Value=0`
  - Matches: `0`, `1`, `100`
  - Does NOT match: `-1`, `-10`

- **lte** or **less_than_or_equal**: Less than or equal (numeric comparison)
  - Example: `Field='returnCode', Operator='lte', Value=5`
  - Matches: `0`, `5`, `-1`
  - Does NOT match: `6`, `100`

- **between**: Value is between min and max (inclusive, numeric comparison)
  - Example: `Field='returnCode', Operator='between', Value=[0, 10]`
  - Matches: `0`, `5`, `10`
  - Does NOT match: `-1`, `11`, `100`

## Troubleshooting Using Logs

### Problem: No cases are being created

**Check the logs for:**

1. **Is the rules engine enabled?**
   ```
   Rules engine is ENABLED
   ```
   If you see `Rules engine is DISABLED`, check your `.env` file for `AUDITSYNC_ENABLE_RULES_ENGINE=true`

2. **Are rules being loaded?**
   ```
   Loaded 2 rules from cache
   ```
   If you see `Loaded 0 rules from cache`, check the database queries in `troubleshooting_rules.sql`

3. **Are rules matching?**
   ```
   ✓ Rule 'Security Team' MATCHED - CreateCase=true, Extractions=3
   ```
   If you see `✗ Rule 'XXX' DID NOT MATCH`, check which condition failed and why

4. **Is createCase enabled?**
   ```
   ✓ Rule 'Security Team' MATCHED - CreateCase=true
   ```
   If you see `CreateCase=false`, update the ACTIONS column in the database

5. **Was the case actually created?**
   ```
   Rule 'Security Team' matched - Created case case-abc123 with 3 extraction(s) for message 9999916_133_0 (offset: 123)
   ```
   If you see this, the case was created successfully

### Problem: Wrong rule is matching

**Check the logs for:**

```
Evaluating Rule #1: 'Security Team' (ORDER_POSITION: 0)
  ...
✗ Rule 'Security Team' DID NOT MATCH
----------------------------------------
Evaluating Rule #2: 'Other' (ORDER_POSITION: 1)
  ...
✓ Rule 'Other' MATCHED
```

Rules are evaluated in ORDER_POSITION order (ascending). The FIRST rule that matches wins (short-circuit logic). If the wrong rule is matching:
- Check the ORDER_POSITION values in the database
- Verify conditions for higher-priority rules are correct
- Consider adjusting ORDER_POSITION to change evaluation order

### Problem: Condition is not matching expected values

**Example log:**
```
Evaluating Condition #1: Field='name', Operator='equals'
    Field Value: 'subscribers'
    Operator: 'equals' with expected value: 'SUBSCRIBERS' → Result: NO MATCH
```

**Issue**: `equals` operator is case-sensitive. `subscribers` ≠ `SUBSCRIBERS`

**Solution**: Either:
- Change the expected value in the database to match the actual case
- Use `contains` operator instead (case-insensitive)
- Or change the data source to use consistent casing

### Problem: Regex is timing out

**Example log:**
```
Regex timeout for pattern: ^(?:SELECT.*FROM.*WHERE.*){100}$
```

**Issue**: Complex regex pattern taking > 1 second to evaluate

**Solution**:
- Simplify the regex pattern
- Use multiple simpler conditions instead of one complex regex
- Consider using `contains` operator for simple substring matching

## Configuration

To see detailed logs, ensure your application is configured with appropriate log levels:

**.env file:**
```
LOGGING__LOGLEVEL__DEFAULT=Information
LOGGING__LOGLEVEL__AUDITSYNC.ORACLECONSUMER.APPLICATION.SERVICES.RULESENGINESERVICE=Information
```

**appsettings.json:**
```json
{
  "Logging": {
    "LogLevel": {
      "Default": "Information",
      "AuditSync.OracleConsumer.Application.Services.RulesEngineService": "Information"
    }
  }
}
```

For even more verbose output, use `Debug` level:
```
LOGGING__LOGLEVEL__AUDITSYNC.ORACLECONSUMER.APPLICATION.SERVICES.RULESENGINESERVICE=Debug
```
